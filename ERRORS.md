# MTDB Errors

MTDB сообщает ошибки через стандартные объекты JavaScript `Error`.

Для программной обработки необходимо использовать свойство:

```js
error.code
```

Пример:

```js
try {
  db.read('users/1.json');
}

catch (error) {
  if (error.code === 'MTDB_CLOSED') {
    // База уже закрыта
  }

  throw error;
}
```

Текст `error.message` предназначен для диагностики и не является стабильным API.

Логика приложения должна опираться на `error.code`.

---

# Категории ошибок

Ошибки MTDB условно делятся на:

* ошибки входных данных;
* ошибки структуры виртуальной файловой системы;
* ошибки состояния экземпляра;
* writer-lock ошибки;
* ошибки формата и повреждения данных;
* ошибки recovery;
* ошибки compact;
* ошибки записи;
* системные ошибки Node.js и ОС.

---

# Ошибки входных данных

## MTDB_INVALID_FILE_PATH

Передан некорректный путь к `.mtdb`.

Пример:

```js
mtdb.open('');
```

или:

```js
mtdb.open(null);
```

Текущий экземпляр:

```text
не создан
```

Рекомендуемое действие:

```text
исправить аргумент и повторить open()
```

---

## MTDB_INVALID_FILE_EXTENSION

Файл базы не имеет расширения `.mtdb`.

Пример:

```js
mtdb.open('./data.db');
```

Правильно:

```js
mtdb.open('./data.mtdb');
```

Текущий экземпляр:

```text
не создан
```

Рекомендуемое действие:

```text
исправить путь
```

---

## MTDB_INVALID_PATH

Передан некорректный внутренний путь MTDB.

Причинами могут быть:

* абсолютный путь;
* Windows drive path;
* drive-relative path;
* пустой путь там, где root не разрешён;
* пустой сегмент;
* `.` или `..`;
* trailing slash;
* NUL-символ.

Примеры:

```text
/users/1.json
C:/users/1.json
C:users/1.json
users//1.json
users/../1.json
users/
```

Текущий экземпляр:

```text
можно продолжать использовать
```

Рекомендуемое действие:

```text
исправить path
```

---

## MTDB_PATH_TOO_LONG

Внутренний путь превышает максимальную длину.

Текущий лимит:

```text
1024 байта UTF-8
```

Текущий экземпляр:

```text
можно продолжать использовать
```

---

## MTDB_JSON_EXTENSION_REQUIRED

JSON-path не заканчивается на `.json`.

Пример:

```js
db.read('users/1');
```

Правильно:

```js
db.read('users/1.json');
```

Текущий экземпляр:

```text
можно продолжать использовать
```

---

## MTDB_INVALID_JSON

Переданное значение невозможно сериализовать через `JSON.stringify()`.

Пример:

```js
const value = {};
value.self = value;

db.write('value.json', value);
```

Также возникает, если top-level значение сериализуется в `undefined`:

```js
db.write('value.json', undefined);
```

Текущий экземпляр:

```text
можно продолжать использовать
```

Никакая mutation в базу до возникновения этой ошибки не выполняется.

---

## MTDB_JSON_TOO_LARGE

Сериализованный JSON превышает максимальный размер.

Текущий лимит:

```text
100 MiB
```

Размер определяется после:

```js
JSON.stringify(value)
```

и преобразования результата в UTF-8.

Текущий экземпляр:

```text
можно продолжать использовать
```

---

# Ошибки виртуальной структуры

## MTDB_DIRECTORY_NOT_FOUND

Требуемый каталог не существует.

Пример:

```js
db.write('users/1.json', {});
```

если `users` ранее не создан.

Правильно:

```js
db.mkdir('users');
db.write('users/1.json', {});
```

Также может возникнуть:

```js
db.list('missing');
```

Текущий экземпляр:

```text
можно продолжать использовать
```

---

## MTDB_PATH_IS_FILE

Путь, который должен быть каталогом, занят JSON-файлом.

Пример:

```js
db.write('data.json', {});

db.mkdir('data.json/users');
```

Текущий экземпляр:

```text
можно продолжать использовать
```

---

## MTDB_PATH_IS_DIRECTORY

Путь, который должен быть JSON, занят каталогом.

Пример:

```js
db.mkdir('users/data.json');

db.write('users/data.json', {});
```

Также может возникнуть при:

```js
db.read(...);
db.delete(...);
```

Текущий экземпляр:

```text
можно продолжать использовать
```

---

# Ошибки состояния экземпляра

## MTDB_ALREADY_OPEN

База уже открыта writer-процессом.

Может возникнуть:

* при втором `open()` в том же процессе;
* если база уже открыта другим процессом.

Пример:

```js
const first = mtdb.open('./data.mtdb');

const second = mtdb.open('./data.mtdb');
```

Второй вызов завершится:

```text
MTDB_ALREADY_OPEN
```

Рекомендуемое действие:

```text
использовать уже открытый экземпляр или дождаться закрытия writer
```

---

## MTDB_CLOSED

Операция вызвана после успешного `db.close()`.

Пример:

```js
db.close();

db.read('settings.json');
```

Текущий экземпляр:

```text
окончательно закрыт
```

Рекомендуемое действие:

```text
создать новый экземпляр через mtdb.open()
```

---

## MTDB_RECOVERY_REQUIRED

Во время изменения базы произошла ошибка, после которой MTDB больше не гарантирует согласованность runtime-состояния текущего экземпляра.

После этой ошибки запрещены:

```text
mkdir
list
read
write
delete
compact
```

Разрешён:

```js
db.close();
```

Правильное восстановление:

```js
db.close();

const db2 = mtdb.open('./data.mtdb');
```

Следующий `open()` выполнит recovery, если база осталась `DIRTY`.

Важно: `MTDB_RECOVERY_REQUIRED` обычно является ошибкой **последующих** операций.

Первая операция, вызвавшая проблему, может вернуть исходную ошибку, например:

```text
EIO
ENOSPC
EPERM
EACCES
MTDB_WRITE_FAILED
```

После этого экземпляр переходит в состояние recovery-required.

Рекомендуемое действие:

```text
не выполнять больше никаких операций кроме close(); затем открыть базу заново
```

---

## MTDB_REENTRANT_OPERATION

Публичная операция MTDB была вызвана внутри уже выполняющейся операции того же экземпляра.

MTDB использует синхронную последовательную модель и запрещает reentrant operations.

Текущий экземпляр:

```text
можно продолжать использовать
```

Вложенная операция не добавляется в очередь и не выполняется позднее.

---

## MTDB_OPERATION_INCOMPLETE

Внутренняя защита обнаружила, что синхронная операция не была завершена после обработки очереди.

При корректной работе библиотеки пользователь не должен получать эту ошибку.

Классификация:

```text
internal invariant failure
```

Рекомендуемое действие:

```text
закрыть базу и рассматривать ошибку как дефект библиотеки
```

---

# Writer-lock ошибки

## MTDB_SYMLINK_UNSUPPORTED

Writer пытается открыть `.mtdb` через symbolic link.

Пример:

```text
alias.mtdb -> data.mtdb
```

MTDB запрещает такой способ открытия, чтобы один физический файл нельзя было одновременно открыть под разными именами.

Рекомендуемое действие:

```text
открывать реальный .mtdb напрямую
```

---

## MTDB_HARDLINK_UNSUPPORTED

Физический `.mtdb` имеет более одной hardlink-ссылки.

Это запрещено для writer-защиты.

Рекомендуемое действие:

```text
удалить дополнительные hard links и использовать один канонический файл
```

---

## MTDB_LOCK_GUARD_EXISTS

Существует:

```text
<database>.mtdb.lock.guard
```

Guard используется для сериализации восстановления stale writer-lock.

MTDB намеренно не удаляет его автоматически, потому что безопаснее временно заблокировать writer, чем допустить два writer одновременно.

Такое состояние может остаться после аварийного завершения процесса непосредственно во время lock recovery.

Рекомендуемое действие:

1. Убедиться, что никакой MTDB writer не работает с этой базой.
2. Убедиться, что другой процесс не выполняет lock recovery.
3. Только после этого удалить stale `.lock.guard`.
4. Повторить `open()`.

---

## MTDB_CORRUPTED_LOCK

Файл writer-lock существует, но его содержимое невозможно безопасно распознать.

Причины:

* некорректный JSON;
* отсутствующий PID;
* некорректный PID;
* отсутствующий token;
* повреждённый token.

MTDB намеренно не удаляет такой lock автоматически.

Рекомендуемое действие:

```text
сначала убедиться, что writer действительно отсутствует; затем очистить lock вручную
```

---

## MTDB_LOCK_CHANGED

Внутренняя ошибка координации writer-lock.

Означает, что lock исчез во время проверки.

В нормальных race-сценариях библиотека обрабатывает это состояние самостоятельно.

Публичный пользователь обычно не должен получать этот код.

Классификация:

```text
internal coordination state
```

---

## MTDB_LOCK_OWNERSHIP_LOST

При освобождении writer-lock обнаружено, что lock больше не принадлежит текущему экземпляру.

Это может означать:

* ручное изменение `.lock`;
* вмешательство другого процесса;
* внешнее повреждение lock-файла.

Если ошибка возникла во время `close()`, сам `.mtdb` file descriptor уже может быть закрыт.

Рекомендуемое действие:

```text
не продолжать использовать старый экземпляр и проверить lock-файлы
```

---

# Ошибки файла и формата

## MTDB_PATH_NOT_FILE

Путь `.mtdb` существует, но не является обычным файлом.

Например, по этому пути находится каталог.

Рекомендуемое действие:

```text
исправить путь
```

---

## MTDB_CORRUPTED_FILE

Файл физически не соответствует минимальным требованиям MTDB.

Например:

* файл меньше минимального размера;
* нарушена базовая структура файла.

Рекомендуемое действие:

```text
не использовать файл до восстановления из корректной копии
```

---

## MTDB_INVALID_MAGIC

Начальная сигнатура файла не соответствует MTDB.

Обычно означает, что передан:

* не MTDB-файл;
* повреждённый MTDB-файл.

Рекомендуемое действие:

```text
проверить выбранный файл или восстановить корректную копию
```

---

## MTDB_UNSUPPORTED_VERSION

Версия формата `.mtdb` не поддерживается текущей версией библиотеки.

Пример:

```text
библиотека поддерживает format v2, файл имеет другую версию
```

Рекомендуемое действие:

```text
использовать совместимую версию MTDB или выполнить официальную миграцию формата
```

Нельзя просто менять version byte вручную.

---

## MTDB_INVALID_HEADER

Header MTDB имеет некорректные значения.

Например, неправильный data offset.

Рекомендуемое действие:

```text
считать файл повреждённым
```

---

## MTDB_INVALID_HEADER_STATE

Поле состояния header имеет неизвестное значение.

Допустимые состояния:

```text
CLEAN
DIRTY
```

Любое другое значение считается повреждением.

---

## MTDB_INVALID_INDEX

Метаданные индексной области не соответствуют формату.

Например, header содержит неправильный bucket count.

Не путать с:

```text
MTDB_CORRUPTED_INDEX
```

`MTDB_INVALID_INDEX` относится прежде всего к структуре формата/header.

---

## MTDB_UNEXPECTED_EOF

MTDB ожидала прочитать определённое количество байт, но файл закончился раньше.

Это может означать:

* внешнее усечение файла;
* повреждение структуры;
* неожиданную I/O-проблему.

В recovery специальный незавершённый tail обрабатывается отдельно. Поэтому публично дошедший `MTDB_UNEXPECTED_EOF` следует считать серьёзной ошибкой.

Рекомендуемое действие:

```text
закрыть экземпляр и проверить целостность файла
```

---

# Ошибки целостности данных

## MTDB_CORRUPTED_INDEX

Bucket index содержит некорректную ссылку или цепочку.

Примеры:

* offset выходит за допустимые границы;
* bucket указывает на `COMMIT`;
* `previousOffset` направлен вперёд;
* запись принадлежит другому hash bucket.

MTDB умеет автоматически попытаться восстановить индекс через журнал.

Поэтому многие повреждения индекса пользователь вообще не увидит.

Если `MTDB_CORRUPTED_INDEX` всё же дошёл наружу, автоматическое восстановление не смогло полностью скрыть проблему.

Рекомендуемое действие:

```text
закрыть базу и открыть заново; если ошибка повторяется, файл требует диагностики
```

---

## MTDB_CORRUPTED_RECORD

Физическая record-запись повреждена.

Причинами могут быть:

* неправильный record magic;
* неизвестный тип;
* некорректный path length;
* некорректный data length;
* неверный checksum;
* record выходит за границы файла;
* некорректный сохранённый path.

Это серьёзное повреждение подтверждённых данных.

Recovery не должен молча игнорировать повреждённую подтверждённую record.

Рекомендуемое действие:

```text
не продолжать обычную эксплуатацию базы; восстановить данные из корректной копии или провести диагностику
```

---

## MTDB_CORRUPTED_JSON

Record физически прошла проверки формата и checksum, но сохранённый payload невозможно разобрать через `JSON.parse()`.

Это отличается от `MTDB_CORRUPTED_RECORD`.

Физическая record считается целой, но содержащийся JSON некорректен.

Другие записи базы могут оставаться доступными.

Повреждённый path можно восстановить новой записью, если состояние базы в остальном корректно.

---

## MTDB_CORRUPTED_LOG

Нарушена структура recovery-журнала.

Примеры:

* `COMMIT` без ожидающей mutation;
* новая mutation до `COMMIT` предыдущей;
* `COMMIT` относится к другому path;
* `COMMIT.previousOffset` не указывает на подтверждаемую record;
* `previousOffset` не соответствует предыдущей записи bucket-chain.

Это означает, что recovery не может однозначно определить подтверждённое логическое состояние.

Рекомендуемое действие:

```text
не изменять файл; провести диагностику или восстановить резервную копию
```

---

# Ошибки compact

## MTDB_COMPACT_VALIDATION_FAILED

Новый compact-файл был полностью создан, но его проверка обнаружила несогласованность.

Основной `.mtdb` не должен заменяться таким файлом.

Рекомендуемое действие:

```text
считать compact неуспешным и сохранить исходную базу
```

---

## MTDB_COMPACT_FAILED

Внутренняя ошибка операции compact.

Например, compact обнаружил неподдерживаемое значение offset во временном индексе.

Рекомендуемое действие:

```text
не считать compact завершённым; основной файл должен оставаться источником истины
```

---

# Ошибки записи

## MTDB_WRITE_FAILED

Низкоуровневая запись через `fs.writeSync()` вернула `0` записанных байт до завершения требуемого Buffer.

Ошибка означает, что MTDB не смогла закончить ожидаемую физическую запись.

Если это произошло внутри mutation, текущий экземпляр может перейти в:

```text
MTDB_RECOVERY_REQUIRED
```

Рекомендуемое действие после mutation failure:

```js
db.close();

const db2 = mtdb.open('./data.mtdb');
```

---

# Внутренние format errors

Следующие ошибки существуют для защиты внутренних инвариантов формата.

При корректном использовании публичного API пользователь обычно не должен их получать.

## MTDB_INVALID_RECORD_TYPE

Внутренняя функция формирования record получила неизвестный тип записи.

Классификация:

```text
internal invariant failure
```

---

## MTDB_INVALID_RECORD_PATH

Внутренняя функция формирования record получила пустой или слишком длинный path.

Публичные пути обычно проходят нормализацию раньше.

Классификация:

```text
internal invariant failure
```

---

# Системные ошибки Node.js / ОС

MTDB не преобразует все ошибки файловой системы в собственные `MTDB_*`.

Поэтому приложение также может получить стандартные системные коды Node.js.

Примеры:

```text
EIO
ENOSPC
EACCES
EPERM
EMFILE
ENFILE
EROFS
ENOENT
EEXIST
```

Это намеренное поведение: исходная ошибка ОС часто содержит наиболее полезную диагностическую информацию.

Пример:

```js
try {
  db.write('users/1.json', user);
}

catch (error) {
  console.error(error.code);
  console.error(error.message);
}
```

Если системная ошибка произошла во время изменения `.mtdb`, нельзя считать, что текущий экземпляр безопасно продолжать использовать.

Последующие операции могут вернуть:

```text
MTDB_RECOVERY_REQUIRED
```

После такой ошибки безопасный шаблон:

```js
try {
  db.write('users/1.json', user);
}

catch (error) {
  try {
    db.close();
  }

  catch {}

  throw error;
}
```

Перед продолжением работы база должна быть открыта заново.

| `MTDB_INVALID_PATH`            | Можно                                      |
| `MTDB_PATH_TOO_LONG`           | Можно                                      |
| `MTDB_JSON_EXTENSION_REQUIRED` | Можно                                      |
| `MTDB_INVALID_JSON`            | Можно                                      |

| `MTDB_CORRUPTED_RECORD`        | Не рекомендуется                           |
| `MTDB_CORRUPTED_LOG`           | Нет                                        |
| `MTDB_CORRUPTED_INDEX`         | Закрыть/reopen, если код дошёл наружу      |
| `MTDB_UNEXPECTED_EOF`          | Не рекомендуется                           |
| `MTDB_CLOSED`                  | Нет                                        |
| `MTDB_LOCK_OWNERSHIP_LOST`     | Нет                                        |
| write-related system error     | Закрыть и reopen                           |

# Рекомендуемый error handling

Для ошибок входных данных:

```js
try {
  db.write(path, value);
}

catch (error) {
  if (
    error.code === 'MTDB_INVALID_PATH' ||
    error.code === 'MTDB_JSON_EXTENSION_REQUIRED' ||
    error.code === 'MTDB_INVALID_JSON' ||
    error.code === 'MTDB_JSON_TOO_LARGE'
  ) {
    // Исправить входные данные
  }

  else {
    throw error;
  }
}
```

Для recovery-required:

```js
try {
  db.write('users/1.json', user);
}

catch (error) {
  if (error.code === 'MTDB_RECOVERY_REQUIRED') {
    db.close();
  }

  throw error;
}
```

Для неизвестной ошибки записи безопаснее считать экземпляр потенциально требующим reopen:

```js
try {
  db.write('users/1.json', user);
}

catch (error) {
  try {
    db.close();
  }

  catch {}

  throw error;
}
```
